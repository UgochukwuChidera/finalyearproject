PROJECT: DAPE (Differential + AI Pipeline for Form Extraction)
Repository: UgochukwuChidera/finalyearproject

====================================================================
1) HIGH-LEVEL PURPOSE
====================================================================
This project extracts structured data from scanned/photographed forms using a
hybrid approach:

- Classical computer vision (alignment + differential analysis) to localize
  handwritten/changed regions.
- Multimodal LLM extraction (via OpenRouter) for transcription and field value
  prediction.
- Confidence scoring + optional dictionary matching + validation rules to
  determine whether a field is auto-accepted, spot-checked, or escalated for
  review.
- Human-in-the-loop (HITL) review workflow to correct uncertain fields.
- Multi-format export and audit logging for downstream analysis.

It supports both CLI processing and a Flask web application for end-to-end
operations (config management, uploads, review, audits, evaluation, settings).

====================================================================
3) CORE DATA FLOW (FORM PROCESSING PIPELINE)
====================================================================
Primary function: main.py -> process_form(...)

Stage 1: Config + dependencies loading
- Loads config from configs/<name>.json (or explicit config path)
- Loads optional template_extraction baseline JSON (for text diffing)
- Loads dictionaries from dictionaries/*.csv
- Reads confidence weights and thresholds from config

Stage 2: Image preprocessing and quality/statistics extraction
- load_image() -> grayscale conversion
- baseline metrics
- skew analysis + optional deskew
- illumination normalization
- adaptive binarization
- border removal
- feature/statistics fusion score calculation

Stage 3: Template alignment
- Loads blank template image from config.template_path
- Uses ORB keypoints + BFMatcher + RANSAC homography
- Produces aligned form image and alignment confidence metadata

Stage 4: Differential analysis
- Computes absolute difference between aligned form and template
- Applies threshold + morphological cleanup + dilation
- Builds binary mask of changed/ink regions
- Computes deviation metadata (region count, ratio)

Stage 5: Prompt/image package construction
- Builds multi-image prompt payload:
  * Full aligned form image prompt
  * Optional non-critical field reminder prompt
  * One ink-only crop prompt per critical field
- Critical fields are cropped using scaled bounding boxes and differential mask

Stage 6: AI extraction
- GeminiClient (OpenAI SDK with OpenRouter base URL) sends multimodal request
- Enforces JSON response format
- Normalizes response shape to pipeline contract:
  {"fields": {...}, "meta": {...}}
- Handles alternate wrappers and list->dict normalization
- Computes per-field C_lp confidence from token logprobs where possible
- Applies confidence fallback logic when logprobs are absent/incomplete

Stage 7: Field-level postprocessing
For each configured field:
- Reads AI raw value
- For non-critical fields:
  * compares with template baseline; unchanged values can be nullified
  * checkboxes coerced to boolean when present
- For critical fields:
  * dictionary match can be applied (if configured)
- Computes:
  * C_lp (LLM confidence proxy)
  * C_dict (dictionary similarity confidence)
  * C_final (weighted final confidence)
- Applies thresholding:
  * accepted
  * spot_check
  * pending_review
- Runs semantic/rule validation (regex/min/max/min_length) and can force review
- Persists crop path and full field audit metadata

Stage 8: Output structuring + export
- OutputStructurer converts validated fields into structured object
- DataExporter writes JSON + CSV
- RelationalXLSXExporter writes multi-sheet analytical workbook

Stage 9: Audit logging
- AuditLogger writes:
  * per-job JSON log under logs/
  * append-only JSONL stream at outputs/audit.jsonl
- Includes extraction confidences, statuses, review summary, and export paths

Stage 10: Return payload
- Returns job status, fields, pending fields, structured output, export paths,
  resolved config path, and AI debug bundle

====================================================================
4) ARCHITECTURAL LAYERS AND MAJOR MODULES
====================================================================
A) Presentation/Web Layer (web/)
- Flask blueprint with HTML templates
- Maintains in-memory job registry (JOBS dict + lock)
- Starts background worker threads for uploads
- Exposes both HTML pages and JSON API endpoints

B) Orchestration Layer (main.py)
- Coordinates all domain services/modules
- Owns overall pipeline control flow and job-level assembly

C) AI Extraction Layer (ai_extraction/)
- gemini_client.py:
  * model resolution (env -> models.json -> built-in default)
  * OpenRouter API interaction and retry logic
  * payload normalization and confidence derivation
- prompt_builder.py:
  * extraction prompts and discovery prompt generation
- confidence.py:
  * Levenshtein, C_lp, C_final utility functions
- dictionary_matcher.py:
  * dictionary loading and nearest-match scoring

D) Vision/Document Processing Layer (project/)
- preprocessing/*: grayscale, skew, illumination, binarization, border removal
- alignment/aligner.py: geometric registration to template
- differential/analyzer.py: changed-ink region detection
- validation/*: semantic + confidence validation abstractions
- hitl/*: correction application and standalone HITL review server
- output/*: structuring and multi-format export

E) Evaluation Layer (evaluation/)
- offline metric computation against ground truth
- supports pre-HITL and simulated post-HITL comparisons
- writes full_results.json used by web evaluation dashboard

====================================================================
5) CONFIGURATION MODEL
====================================================================
Per-template config JSON (configs/*.json) typically defines:
- template_path: blank reference form image
- fields: list of field definitions
  * name
  * label / label_hint
  * type / expected_type
  * critical (boolean)
  * bounding_box
  * optional dictionary reference
  * optional validation constraints
- editor_canvas: normalization coordinate system for box scaling
- confidence_weights (w_lp, w_dict)
- thresholds (auto_accept, review)
- optional template_extraction path for baseline text diffing

Model config:
- models.json stores active model + model catalog for settings page
- OPENROUTER_MODEL environment variable overrides active model at runtime

Environment variables:
- OPENROUTER_API_KEY (required for AI calls)
- OPENROUTER_MODEL (optional runtime override)

====================================================================
8) CONFIDENCE, VALIDATION, AND REVIEW LOGIC
====================================================================
Confidence composition:
- C_lp: LLM confidence proxy derived from logprobs / fallback
- C_dict: dictionary-similarity confidence (mainly useful for critical fields)
- C_final: weighted combination normalized by active weights

Decision thresholds:
- C_final >= auto_accept          -> accepted
- review <= C_final < auto_accept -> spot_check
- C_final < review                -> pending_review

Semantic/rule validation:
- Additional checks can force pending_review even with high confidence

Human-in-the-loop:
- Pending fields are surfaced in web review UI
- Reviewer corrections update final_value/status and are auditable
- Review events are appended to outputs/audit.jsonl

====================================================================
9) EVALUATION SUBSYSTEM
====================================================================
run_evaluation.py + evaluation/evaluator.py:
- Loads forms from directory by extension
- Runs DAPE pipeline extraction per form
- Compares against ground truth field-by-field
- Computes:
  * exact/normalized text metrics
  * checkbox precision/recall/F1
  * escalation and correction statistics
  * pre-HITL vs post-HITL improvement
- Writes evaluation/results/full_results.json
- Web dashboard /evaluation visualizes results

====================================================================
10) DESIGN CHARACTERISTICS
====================================================================
Strengths:
- Hybrid CV+LLM strategy reduces dependence on pure OCR
- Critical-field specialization through differential ink crops
- Config-driven template support (no hardcoded form layout)
- Built-in traceability via detailed audit logging
- Practical HITL integration for low-confidence extractions
- Multiple exports suitable for operations and analytics

Operational considerations:
- In-memory JOBS state is process-local (non-persistent queue)
- Web job execution uses Python threads; scaling would require external workers
- Accuracy and latency depend on model behavior and template quality
- Good alignment and reliable bounding boxes are central to performance

====================================================================
12) SUMMARY
====================================================================
This repository implements a full document-understanding workflow tailored for
structured forms: ingest -> preprocess -> align -> detect handwritten changes ->
LLM extraction -> confidence + validation -> HITL correction -> export + audit
-> evaluation. The architecture is modular, config-driven, and focused on
balancing automation with controlled review for reliability in real-world form
processing.
